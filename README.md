# PySpark Sales Data Transformation

A small PySpark project that reads sales data from CSV, cleans it, joins it with a product catalog, 
and runs aggregations — first using default Spark settings, then again using two basic optimization 
techniques (`cache()` and `repartition()`), to compare the two.

Built to practice core Spark concepts relevant to a data engineering role: DataFrame transformations, 
joins, aggregations, Spark SQL, and a simple, realistic look at why optimization techniques matter.

## Problem

Given raw order-level sales data and a separate product catalog, calculate total 
revenue by product category and by region — a common reporting task.

The raw orders data has typical data-quality issues: duplicate rows, some missing quantities, 
and inconsistent text casing in the status field (`"completed", "Completed", "COMPLETED"`).

## Dataset

- `data/raw/orders.csv` — 20,200 order records (order_id, product_id, region, quantity, order_date, status)
- `data/raw/products.csv` — 10 products (product_id, product_name, category, unit_price)

Both are generated by `src/generate_data.py` so the project runs locally without needing an 
external dataset. The dataset is intentionally small — this project demonstrates transformation 
logic clearly rather than testing Spark at big-data scale.

## What the pipeline does

1. **Clean** — remove duplicate rows, drop rows with missing quantity, and normalize the `status` 
   column (lowercase, trimmed)
2. **Filter** — keep only orders where `status == "completed"`
3. **Join** — join cleaned orders with the product catalog on `product_id`
4. **Aggregate** — calculate total revenue by category and by region
5. **Spark SQL** — perform similar aggregations using SQL against a temporary view
6. **Optimize** — re-run the pipeline using `.cache()` and `.repartition()` and compare the execution 
   time with the basic version

## Setup & Usage

Requires Python and Java (Spark needs a JVM) installed locally.

```bash
# 1. Install dependencies
pip install -r requirements.txt

# 2. Generate the sample dataset
python src/generate_data.py

# 3. Run the basic version
python src/basic_transform.py

# 4. Run the optimized version
python src/optimized_transform.py

# 5. Run the Spark SQL version
python src/spark_sql_queries.py

# 6. Run both versions and compare timing
python src/compare_runs.py
```

## Verified Run

The project was tested locally with the generated 20,200-row orders dataset.

The basic and optimized versions produced the same revenue results.

Actual timing from the local run:

```
Basic:     11.4s
Optimized: 13.39s
```

The optimized version was slightly slower on this small dataset. This can happen because 
`cache()` and `repartition()` introduce their own overhead, and the dataset is not large enough 
for the optimization to provide a measurable benefit.

## Optimization Notes

`.cache()` is used because the joined DataFrame is reused for two separate aggregations — by category and by region. 
Caching can avoid recomputing the same DataFrame when it is reused.
`.repartition()` is used to explicitly repartition the data before aggregation. 
Repartitioning involves a shuffle, so it can add overhead.

For this small local dataset, the additional overhead meant that the optimized version was slightly 
slower than the basic version. This demonstrates an important Spark concept: optimization techniques are 
not automatically faster for every workload, and their benefit depends on factors such as data size and reuse.
